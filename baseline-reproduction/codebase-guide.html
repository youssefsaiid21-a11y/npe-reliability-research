01 / Start with the question

Simulation goes forwards. Inference goes backwards.

Forward simulation

Choose parameters and random inputs. The simulator generates a time series.

Parameters θ → simulator → observations x

This is needed to generate new validation datasets. Our current runner does not do it.

Neural posterior estimation

Give a trained estimator an observation. It returns a distribution of plausible parameter combinations.

Observation x → trained estimator → q(θ | x)

We currently exercise this part, using an example saved in the checkpoint.

The trained object represents uncertainty over parameters, rather than a single best-fit answer. The 1k, 10k and 100k labels describe training-budget variants of saved networks. Loading them does not train on those numbers of new datasets.

03 / Understand the dimensions

151 entries do not mean 151 observation times.

The saved input has shape (1, 151, 1): one dataset, 151 entries, one observed series. The network separates the observations from the appended statistics.

100 observed valuesThe time-series branch
51 statisticsThe handcrafted-feature branch

We recompute the statistics as a check. Inference still uses the checkpoint’s saved input, rather than replacing it with the recomputed vector. The recorded maximum absolute feature difference was approximately 5.722 × 10⁻⁶.

What do convolutions, the LSTM and the flow each do?

Convolutions process local patterns at different widths. The LSTM processes their temporal sequence. Handcrafted statistics join the selected temporal representation. The final learned summary conditions a flexible joint distribution over the four parameters. Invertibility belongs to the flow’s parameter-space transformation, not the 151-to-16 observation compression.

Which architectural details must we preserve?

Four blocks contain twelve Conv1D modules. The source does not add an extra ReLU between these convolution blocks. The LSTM code selects the final output timestep; replacing it with a different pooling or hidden-state scheme would change the network. Both the stored standardization and the handcrafted feature definitions must be preserved.

06 / A distinction we must resolve

The bounds do not uniquely define the prior.

Our wrapper imposes uniform-box support using the VOC limits. The authors’ notebook entry point constructs a Gaussian prior; an alternative source path uses a box prior. We have not established the saved checkpoints’ exact training lineage.

Gaussian: midpoint mean, width ÷ 4 standard deviation Uniform over the limits

Schematic one-parameter prior comparison, using limits 0…10. This is not a posterior chart and does not establish checkpoint provenance.

What our sampler currently does

It proposes draws from the learned conditional density and rejects draws outside the configured box.

q_box(θ | x) ∝ q(θ | x) × 1[θ inside limits]

Supplying BoxUniform here does not automatically convert a Gaussian-trained posterior into the correct uniform-prior posterior.

What still needs to be audited

Which source path trained the saved weights; the prior distribution; simulator clipping; requested versus actually simulated parameters; and the validation sampling design.

This is a baseline-alignment issue, separate from the later planned stock/flow/noise misspecification treatments. Existing numerical samples have not been changed to conceal it.

07 / Explore the codebase

Choose a file to see its job.

Our harness and the authors’ larger pipeline are different layers.

The authors’ notebook calls run_training(). Their source also includes Vensim simulation, fresh validation-data generation, training and aggregate metrics. Our runner deliberately bypasses that full entry point and loads the pretrained object directly. The alternative run_experiments()/run_analysis() path should be audited separately rather than treated as interchangeable.

Read active code before trusting a metric’s name or docstring.

The active calculate_coverage_prob() implementation pools interval inclusion across datasets and parameters, returns absolute deviation from nominal coverage, and handles zero coverage specially. Its docstring describes a different ratio score. Our current saved-example runner does not execute that aggregate metric function.

What is safe to change while learning?

The draw count and sampling seed are command-line controls. Plot colours and bins change presentation. The current baseline-config.json is a planning document, not executable configuration. Changing prior limits, feature formulas, parameter order or network structure changes inferential meaning and requires a separate validated study.

The JSON records the latest saved successful run. The NPZ holds local samples. The PNG visualizes their marginals. A failed rerun can leave an older summary in place.
